1. The big picture

Today, every time Claude reads a file, summarises a log, or writes boilerplate, that text goes to Anthropic's servers and counts against your weekly usage. Much of that work is not hard. It is bulk: lots of text in and a modest amount out, with little deep reasoning.

Your graphics card can run a capable open-weight language model entirely on your desk. Offload makes it a second worker:

  • Claude (or whichever cloud agent you use in future) does the thinking: design, tricky logic, deciding what to do, and checking results.
  • The local model does the legwork: reading and summarising files, extracting facts, drafting routine code, and eventually whole well-specified tasks.

The local model is free per use. It costs electricity and nothing else, it has no rate limit, and nothing leaves your machine. The trade-off is that it is less capable than a frontier cloud model, so the whole project is about measuring where it is good enough.

2. What a model actually is

A language model is a very large set of numbers, called weights or parameters, plus a fixed recipe for multiplying text through them. The recipe predicts the next token, a word fragment of about ¾ of a word, then appends it and repeats. That loop is all "generating" is.

When you see 27B in a model name, it means 27 billion parameters. On disk, a model is one file, usually a .gguf for the runtimes we use, holding all those numbers. Running the model means loading that file into memory and doing the multiplications as fast as possible.

Being Java-minded helps here: think of the weights as an immutable array and inference as a pure function, nextToken = f(weights, tokensSoFar). There's no hidden state between calls. Even the "memory" of a conversation is just the whole transcript being fed back in every time.

3. VRAM: the number that decides everything

The multiplications need every weight close to the chip doing the work. Your GPU's own memory, VRAM, is where the model must live to be fast.

AMD Radeon RX 7900 XTX: 24 GB of VRAM. That is the top tier of consumer cards, the same amount as an RTX 4090. It comfortably fits the "~30B" class of models, which is where local models start being genuinely useful for coding work.

Your Ryzen 9 7900X also has a tiny built-in GPU, "AMD Radeon(TM) Graphics", with 0.5 GB. Windows shows both. One of the first checks in Phase 1 is making sure the runtimes use the 7900 XTX and not that one.

The rule of thumb

Size in GB ≈ billions of parameters × bits per weight ÷ 8. Models are normally stored at about 4–5 bits per weight (see quantization), so:

Model sizeAt ~4.5 bits/weightFits in your 24 GB?
8B~5 GBEasily, with lots of room for context
14B~8–9 GBEasily
27B–32B~16–20 GBYes: the sweet spot for your card
70B~40 GBNo. It would spill into system RAM and crawl

The weights are not the only thing in VRAM. The KV cache for your conversation and some runtime overhead also need room. Here is roughly what a 27B model looks like loaded on your card:

model weights ~16.5 GB KV cache ~4 GB ~1.5 free

24 GB total. Weights (orange), context memory (blue), runtime overhead (grey). Illustrative figures; the real ones arrive in section 13.

What happens when it does not fit

Runtimes can put some of the model in your normal system RAM (32 GB on your PC) and run those parts on the CPU. It works, but it is dramatically slower, for the reason explained in the next section but one. A model that is 90% on GPU can easily run at a third of the speed of one that is 100% on GPU. So we aim for everything in VRAM.

Unity is a competitor. When the game project is open in the Editor, Unity uses VRAM too, from hundreds of MB to several GB depending on the scene. A model that just fits while Unity is closed may spill over when it is open. Phase 2 measures exactly this, because both are things you actually run together.

4. Quantization: shrinking a model

Models are trained with each weight as a 16-bit number. Quantization rounds the weights to fewer bits, like saving a photo as a smaller JPEG. You lose a little detail and gain a lot of space.

Name you'll seeBits/weight27B sizeQuality loss
F16 / BF1616~54 GBNone (original)
Q8_0~8.5~29 GBPractically none
Q6_K~6.6~22 GBVery small
Q5_K_M~5.7~19 GBSmall
Q4_K_M~4.8~16.5 GBSmall: the usual default
Q3_K_M~3.9~13 GBNoticeable, especially for code

A common surprise: a bigger model at Q4 usually beats a smaller model at Q8. Parameter count matters more than precision, down to about 4 bits. Below that, quality starts falling off faster. The letters (K_M, K_S) are flavours of the rounding scheme; the number is what matters most.

5. Why speed is about memory, not compute

To produce one token, the GPU has to read essentially every weight once. The arithmetic per weight is tiny, so the bottleneck is how fast the weights can be pulled out of memory: the memory bandwidth.

Bandwidth
RX 7900 XTX VRAM (GDDR6)~960 GB/s
Your system RAM (DDR5-6000, dual channel)~96 GB/s
VRAM is about ten times faster than system RAM. That is the whole reason spilling out of VRAM hurts so much.

This gives you a back-of-envelope speed ceiling:

max tokens/s ≈ bandwidth ÷ GB read per token

For a 27B model at Q4 (~16.5 GB): 960 ÷ 16.5 ≈ 58 tokens/s at the very most. Real runtimes reach perhaps 50–70% of the ceiling, so expect roughly 30–40 tokens/s. That is faster than you can read, and about the pace of a fast cloud model. Your real numbers go in section 13 after Phase 2.

6. Reading is fast, writing is slow

A model handles text in two very different phases:

  • Prompt processing ("prefill") reads your input. All the input tokens are processed in parallel, so the GPU's compute power is the limit, not bandwidth. Expect hundreds to thousands of tokens per second.
  • Generation ("decode") writes the answer one token at a time, each needing a full pass over the weights. This is the slow ~30–40 tokens/s part.

This matters a lot for Offload. "Read these 5 files and give me a 10-line summary" is mostly reading, which your GPU does fast, and it is exactly the kind of job that eats cloud tokens. Asking the local model to write 2,000 lines is slower and riskier. The first things we delegate will be read-heavy, write-light jobs.

The time to first token, how long before anything appears, is mostly prefill. For a huge prompt it can be several seconds even when generation is quick. Phase 2 measures both.

7. Context windows and the KV cache

The context window is how much text the model can consider at once: your prompt, any files and its own answer together. Models advertise big numbers (128K, 256K tokens), but the advertised maximum and what fits on your card are different things.

While working, the model keeps a running memo of everything it has read so far, the KV cache, so it does not recompute it for every new token. That memo grows with every token of context and lives in VRAM next to the weights. Long context = big KV cache = less room.

  • Some runtimes default to a small context, a few thousand tokens, to be safe. That silently truncates big inputs, a classic "why did it ignore half my file?" bug. We always set context explicitly.
  • The KV cache can itself be quantized (for example to 8-bit), which roughly halves its size for a small quality cost. It's another knob Phase 2 tests.
  • Speed also drops as context fills, because there is more cache to read per token.

Rough scale: 1,000 tokens ≈ 750 English words ≈ 40–80 lines of code. A typical Unity C# script is a few thousand tokens.

8. Dense vs mixture-of-experts

A dense model uses all of its weights for every token. A mixture-of-experts (MoE) model is split into many "expert" sub-networks, and a small router picks a few per token. Name format: 30B-A3B means 30B total, about 3B active per token.

  • Memory: all 30B must still sit in VRAM, so it is as big as a dense 30B.
  • Speed: only ~3B are read per token. Using the formula from section 5, the ceiling is roughly ten times a dense model's. MoE models feel very fast.
  • Quality: usually between a dense model of its active size and one of its total size. Smart for its speed, but not always as smart as a dense 27B.

That trade-off, fast-and-decent versus slower-and-smarter, is exactly the kind of thing your "holistic performance" requirement is about. We may end up using both: MoE for quick jobs, dense for harder ones.

9. Runtimes: LM Studio, Ollama, llama.cpp

A runtime is the program that loads a model file and serves it. The important thing to know is that both candidates use the same engine underneath:

LM Studio (desktop app: GUI to browse, download, chat, plus a background server) Ollama (background service: command line, auto-starts, minimal) │ └──▶ llama.cpp (the open-source engine that does the actual maths) │ ├──▶ Vulkan backend ─┐ └──▶ ROCm/HIP backend ─┴──▶ RX 7900 XTX

So differences between them come mostly from which version of the engine they bundle, which GPU backend they use, and their defaults, not from fundamentally different technology. That is why we benchmark both rather than trusting reviews.

Both serve an OpenAI-compatible API on localhost. It is the same HTTP format OpenAI's API uses, which has become the industry's common language. Offload only ever speaks that API, so swapping LM Studio for Ollama, or for something new next year, is a config change.

10. Your AMD card: Vulkan vs ROCm

Most local-AI tutorials assume an NVIDIA card and its CUDA toolkit. Yours is AMD, so some tutorial steps will not match what you see. That is expected, not a mistake on your part.

  • ROCm / HIP is AMD's equivalent of CUDA. Its Windows support has historically lagged Linux and covers some cards better than others.
  • Vulkan is a cross-vendor graphics and compute API, the same family of tech games use. It works on almost any card and on AMD is often surprisingly competitive.
The answer is "it depends on the job", and the runtime matters as much as the backend. Measured overnight on 2026-10-16 with the same model files on every combination (32k context, one request at a time):
  • Reading (prompt processing): ROCm under Ollama wins. It read prompts fastest on every model tested, for example 3,464 tokens/s against 3,175 on Vulkan for Qwen3.6 35B-A3B. Reading is most of the work when the model is summarising your files, so this matters for delegation.
  • Writing (generation): Vulkan wins, and on the biggest model the runtime matters more. On the two smaller models Vulkan was 10–20% faster, for example 143 against 117 tokens/s on Qwen3.6 35B-A3B. On Qwen3.8 27B, LM Studio wrote at 53–63 tokens/s and Ollama at only 38–41 on either backend, so for that model LM Studio on Vulkan is the clear pick. Writing is most of the time for code and long answers.
  • LM Studio's ROCm engine is the one to avoid. It used 7–13 GB more VRAM than everything else for the same model, filled the card, and then slowed to a crawl on long prompts (313 tokens/s reading at 30k, against 2,700–3,200 elsewhere), and on Qwen3.8 27B a request never finished. Ollama's ROCm build does not have this problem, so it is LM Studio's engine, not ROCm itself. Gemma 4 31B confirmed it on 2026-10-16: on LM Studio's ROCm engine it overflowed the card by 2.7 GB into system RAM and ran at a tenth of its speed. The harness now stops any run whose model spills like that within a minute.
  • The best runtime depends on the model. Gemma 4 26B writes fastest on Ollama with Vulkan (125–151 tokens/s against 115–133 on LM Studio) and reads fastest on Ollama with ROCm (3,000+ tokens/s even at 30k). Qwen3.8 27B is the opposite: LM Studio on Vulkan writes 40% faster than Ollama. So the delegation server will pick the runtime per model, which it can, since both speak the same API.
So your "heavier use" question has a split answer: for reading big files ROCm (in Ollama) is ahead, and for writing long code or reasoning Vulkan is ahead. Two copies of a big model will not fit in 24 GB at once, so in practice one backend is the default; the gaps are 10–20%, not night and day, so the default is the one that suits the commonest job.
Your iGPU stays out of it. The small Radeon graphics in your CPU has no memory of its own; it borrows system RAM, which is roughly ten times slower than the 7900 XTX's memory. In every test it sat at 0% load while the 7900 XTX did the work. Ollama ignores it by default. LM Studio can see it, but did not use it for a model that fits in 24 GB. The one case where it might help is a model too big for 24 GB, and that will be measured rather than assumed.

11. How it plugs into Claude (or anyone)

The glue is MCP, the Model Context Protocol. It is an open standard for giving an AI agent extra tools. Claude Code supports it, and so do many other agents and editors, which is why we chose it over anything Claude-specific.

You ──▶ Claude Code (cloud brain) │ "summarise Assets/Scripts/*.cs" ◀── small message, few tokens ▼ Offload MCP server (runs on your PC) │ reads the files itself ▼ LM Studio / Ollama ──▶ RX 7900 XTX │ ▼ summary ──▶ back to Claude ◀── short result, few tokens

The saving comes from the middle: the files never pass through Claude, only the request and the short result. Claude still decides what to delegate and reviews what comes back.

If you ever switch providers, the server and the local model stay exactly the same. You point the new agent at the same MCP server. The only Claude-specific pieces are small instruction files in adapters/.

12. Watching it work

  1. Open Task Manager → Performance. You will see two GPUs. Pick the AMD Radeon RX 7900 XTX one, not "AMD Radeon(TM) Graphics".
  2. Watch Dedicated GPU memory. When a model loads, it jumps by roughly the model's file size. If it barely moves, the model is running on the CPU, which is the problem Phase 1 checks for.
  3. Switch one of the graphs to Compute (click a graph title). It spikes while the model is generating.
  4. In LM Studio, the Developer tab shows the server log for every request, with tokens/s. Ollama's equivalent is ollama ps in PowerShell, which shows what is loaded and how much is on GPU.

The first full benchmark run, 2026-10-15 to 17. Ten model builds were tested; five were kept. Every number below was measured on your PC. The full tables, regenerated after every run, are in bench/results/summary.md. Samples are small (12–40 per test), so a few points either way is noise; the big gaps are real.

Writer and reviewer

Each model reviewed 232 solutions the models had written, without being told whether a bug was there. A reviewer is only useful if it catches bugs and leaves good code alone, because a false alarm sends the writer off to "fix" working code.

Qwen3.6 35B-A3B94%47%87% caught, 42% wrongly failed

The improved prompt (2026-10-18) adds one rule: judge the code only against its specification, and a claimed bug must come with an input the specification covers. Most false alarms had been complaints about things the specification never asked for, such as empty input. Every reviewer raised fewer false alarms, with bugs caught about the same (a few points either way is noise with 53 real bugs). Qwen3.8 is now the most trustworthy reviewer.

So the first trial pairs Gemma 26B writing with Gemma 31B reviewing, tests first. A second model also beat self-review where it could be measured (on Qwen3.8's code, 62% of bugs caught by Gemma 31B against 50% by Qwen3.8 itself), but that rests on only eight bugs.

What thinking is worth

Thinking matters for reading, hardly at all for coding. Pulling facts out of a long document went from 41% to 89% on Gemma 31B and from 38% to 70% on Qwen3.8 when they could think, but every model was under 45% without it. On coding, the best models were already 83–94% without thinking, and thinking cost 4 to 60 times the time. So the delegation server needs two modes: fast (thinking off) for drafts, code and summaries, and careful (thinking on) for extraction that has to be right, at about four minutes a document on Gemma 31B.

Ideas tested and dropped

  • Writing terse code to save tokens (no comments, minified): every model broke more code the harder it compressed. Qwen3.8 fell from 83% to 56%, the 9B from 44% to 6%. Rejected.
  • Stripping comments from code a model reviews: with the improved review prompt, the reviewers raised more false alarms (Gemma 26B 33% to 42%) and caught slightly fewer bugs, and were no faster. The comments tell the reviewer what the code is meant to do, so reviews get the code as written.
  • Bigger, more precise copies of a model (Q6 instead of 4-bit): no measurable gain, slower and larger. 4-bit is the right size here.
  • MTP speculative decoding (the model guesses several words at once): +24% writing speed on the large Qwen3.6 copy, but the smaller copy was already as fast without it.

The "lost requests" were a hidden 10-minute limit, not a broken runtime. On long thinking-on runs, some answers never came back, on every model. It turned out the test framework quietly cuts any request at 10 minutes, below the limits we had set. Sent directly, the same 16 long requests all came back from LM Studio, the slowest after 16 minutes. The limit is now 20 minutes. Two results were marked down by it and will be re-run: Qwen3.8's thinking-on coding (72%, but 87% of the answers that arrived) and its science-question score. The lesson for the delegation server: careful-mode answers can take over 10 minutes, so its own limit has to allow for that.

14. Glossary

TokenThe unit models read and write, about ¾ of an English word.
Parameters / weightsThe model's learned numbers. "27B" = 27 billion of them.
VRAMThe graphics card's own memory. Your 7900 XTX has 24 GB.
GGUFThe model file format llama.cpp-based runtimes load.
QuantizationStoring weights in fewer bits to save memory (Q4, Q8, …).
Context windowHow much text the model can consider at once.
KV cacheThe model's working memory of the context so far. It grows with context and lives in VRAM.
Prefill / prompt processingReading the input. Parallel and fast.
Decode / generationWriting the output one token at a time. Limited by memory bandwidth.
TTFTTime to first token: the wait before output starts.
MoEMixture-of-experts. A big model that only uses part of itself per token.
Offloading (layers)Putting part of a model in system RAM and running it on the CPU when VRAM is full. Slow.
RuntimeThe program that loads and serves a model: LM Studio, Ollama, llama.cpp.
Vulkan / ROCmTwo ways for the runtime to drive your AMD GPU.
OpenAI-compatible APIThe common HTTP format local runtimes serve, which keeps Offload provider-neutral.
MCPModel Context Protocol, the open standard for giving AI agents tools. It is how Claude reaches Offload.
